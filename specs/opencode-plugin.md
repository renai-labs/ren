# OpenCode plugin (`@renai-labs/opencode`)

The plugin makes a user's own OpenCode a Ren client. Local OpenCode sessions keep working beside Ren sessions in the same TUI. The package is `packages/opencode`; its `README.md` and `AGENTS.md` hold what is built and the package rules. This spec holds the plan. Remove a part from here in the change that builds it.

## 1. Decisions

- D1. **Ren as a provider.** The server part registers a provider `ren`. Its language model is an AI SDK `LanguageModelV3` in plugin code, as OpenCode's `claude-agent` provider is. One `doStream` sends the prompt to the brain of the Ren session through the Chat API and streams the remote turn into the local session. The brain runs the tools; the stream reports them as executed by the provider.
- D2. **A Ren session is a local session with a `ren/<model>` model and the metadata `ren: { spaceId, sessionId }`.** The local session ID and the Ren session ID are the same ID.
- D3. **The plugin never selects a brain.** For each Ren root session it calls `chat.access(sessionId)` and gets a URL and a token. Every brain and hand layout works the same way. The plugin enables features from `Session.Capabilities`, not from the layout.
- D4. **Three parts:** the server part (`@opencode/plugin/effect`), the TUI part (`@opencode/plugin/tui`) and the RPC contract between them (`@opencode/plugin/rpc`).
- D5. **Stock OpenCode only.** No patched OpenCode. `effect` and `@opencode/plugin` come from the host.
- D6. **Commands are `/ren:<command>`.** Built-in commands keep their names and act on Ren sessions through hooks and events.
- D7. **Published alone.** The build bundles `@ren/client`, `@ren/chat`, `@ren/schema` and `@ren/protocol`.
- D8. **Each feature is one commit with its tests.** Write the test first. Add an end-to-end test where a real brain and a real OpenCode host can run.

## 2. Facts the design depends on

Read in OpenCode 2.3.0 source (the dependency is 2.2.6) and Ren. Facts marked _(run)_ were run on 2.2.6 by the plugin's tests, which host OpenCode in-process with the plugin loaded from its directory. Facts marked _(TUI)_ were run by hand in the stock OpenCode 2.2.6 TUI (`opencode --standalone` with isolated `XDG_*` directories and the fake Ren of `test/lib/ren.ts`); no test runs the TUI, because OpenCode does not publish it.

- F1. A plugin cannot write assistant messages or tool parts into a session. The model stream is the only path. `session.prompt` (with `id`, `metadata`, `resume`) admits a real user message.
- F2. The runner gives each model request the header `x-opencode-session-id`, and it reaches `doStream`. The `model.request` hook gets `sessionID`, `kind` (`primary`, `compaction`, `title`, `generate`), `model` and mutable `headers`; a header it sets reaches `doStream` _(run)_. In 2.2.6 the `context` hook's messages carry the message `id` but not its stored `metadata` (2.3.0 adds that), and no type: `ctx.session.context` returns the stored messages with `type`, `id`, `text`, `metadata` and the assistant's `error` and `time.completed` _(run)_.
- F3. `doStream` gets no `abortSignal`. A stop cancels the returned `ReadableStream`; its `cancel` is the stop signal _(run)_.
- F4. A step whose tools are all provider-executed does not continue. One remote turn is one local step. A steer admitted during the step is delivered after it.
- F5. A provider-executed tool result keeps no `metadata`. The TUI's edit diff and subagent link read `metadata`, so those rows show as generic rows (limit L1).
- F6. A plain `Error` on the stream is retryable in OpenCode until the turn has produced output. A retry calls `doStream` again. The plugin's `retry` hook turns retries off for `ren`, as `claude-agent` does, because the brain retries model calls itself; a `doStream` can still run again for messages the brain has (a restart resumes the session), so the plugin asks the brain which messages it has before it sends, and sends with the local message ID as the prompt `id` _(run)_.
- F7. The `title` and `compaction` hooks accept a `result` that skips the model call (compaction _(run)_, F36c). `title`, `compaction` and `generate` requests reach the provider unless a hook supplies the result. A title `result` of `""` skips the model and keeps the session untitled, and OpenCode runs the title hook again at the next prompt while the session is untitled _(run)_.
- F8. Cost comes only from catalog prices of the model. The stream cannot report a cost.
- F9. `experimental.session.import` creates a session with a chosen ID, metadata and model. It cannot append. `session.remove` then import with the same ID works, in one OpenCode process and after a restart on the same database _(run)_.
- F10. The TUI user message shows text, files and skills only. It reads no metadata and has no slot.
- F11. The TUI composer's `@` file search and `!` shell act on the local machine. A plugin cannot add autocomplete sources.
- F12. A slash command name is split on white space (`parseSlashHead` in the 2.2.6 TUI), and a keymap command checks only that its ID is set, so `ren:space` is a valid name. A slash command without `arguments` runs from the completion list _(TUI)_.
- F13. Chat API events are not replayed on reconnect. After `server.connected` the client reads the resources again. A client token reaches only `/chat/*`, lasts 60 minutes, and carries the session ID; the brain sets the sender from the token.
- F14. Ren has no presence, no fork and no unarchive. `session.rename` is on the Chat API only. Ren's import endpoint is `session.import` (F36m).
- F15. _(run)_ An external plugin's `effect` runs with only `Scope` and the loggers in its context (`Plugin.load` in OpenCode's `packages/core/src/plugin.ts`). The plugin provides its own platform services: `FetchHttpClient` from `effect/http`, and Bun or `node:` APIs for files, because `effect`'s `FileSystem` needs a platform package that OpenCode does not provide to plugins.

- F16. `Provider.aisdk` is internal to OpenCode Core in 2.2.6 and not in `@opencode/plugin/effect`. A plugin's provider sets `package: "aisdk:<package>"`; the `sdk` hook's `event.package` is the name without the prefix, and the request's `providerOptions` key is the provider ID _(run)_.
- F17. A model ref with no chosen variant has `variant: "default"` in hooks _(run)_.
- F18. A model with `limit.context: 0` is never compacted automatically: the compaction ceiling of a window of 0 is infinite, and the output limit falls back to the catalog's _(run)_.
- F19. A plugin entry `{ "package": "<directory>", "options": { … } }` in `plugins` loads the server part from the directory's `exports` and passes the options as `ctx.options` _(run)_.
- F20. Brain event order, run on a real brain: a prompt to an idle session gives `session.inbox.enqueued`, `session.execution.started`, then `session.inbox.delivered` with `inboxID` equal to the prompt `id`, then the steps. A steer into a running execution is enqueued during the step, delivered after that step's `session.step.ended`, and answered by a new step of the same execution, which ends with `session.execution.succeeded`. So a local turn starts at the `delivered` of one of its messages and ends at the execution's end, or at the `delivered` of another user message once its own were delivered (F33, the mirror).
- F21. `session.create` with `message` gives the first message to the brain when it starts, before a client can open the event stream, so its delivery cannot be seen. The plugin creates the session without a message and sends the first message with Chat API `session.prompt` after it subscribed.
- F22. Effect's default `ConfigProvider` copies the environment at its first use, so the plugin reads `REN_URL` and `REN_TOKEN` once per OpenCode process. The credentials file is read on each request.
- F23. Plugin RPC: a method needs both `input` and `output` schemas; an RPC that a plugin did not register answers `rpc.unavailable`. The server decodes the input and encodes the output with the schema, and the Effect client decodes the output. The Promise client (`context.client` in the TUI) types only `Rpc.PortableDefinition` (Standard Schema or JSON Schema), returns the server's JSON without decoding it, and rejects with a plain `{ type, message, data? }` object. `Schema.toStandardSchemaV1` returns a value that is both an Effect schema and a Standard Schema, so one definition serves both clients when its schemas encode to themselves _(run)_. A declared error is `context.error(type, message, data)` returned as the handler's failure _(run)_.
- F24. RPC events reach every subscriber of the server as `rpc.<id>.<name>`; the event stream starts with `server.connected` once the subscription is live, so a test can wait for it before it acts _(run)_.
- F25. Plugin storage (`ctx.storage`) is OpenCode's global key-value table in its database, namespaced by plugin ID: one value for every location and process _(run)_.
- F26. `ctx.session.create` accepts `id`, `title`, `model`, `metadata`, `location` and `permissions`; a session created with a `ren/<model>` model and `metadata` keeps both _(run)_.
- F27. The TUI process installs the host's `effect` and `@opencode/plugin` for plugins (`ensurePluginRuntime`) and OpenTUI's Solid runtime plugin support, which compiles a plugin's `.tsx` and provides `solid-js` and `@opentui/*`. Importing the RPC contract with Effect schemas in the TUI part is safe _(TUI)_. `home.footer.status` and `prompt.footer.status` slots take JSX; `ui.dialog.select` marks `current`, takes `search`, and returns `undefined` on escape _(TUI)_.
- F28. Ren's web app creates a session at its first message and calls `chat.prepare` (which wakes a space's shared brain at most once per 5 minutes) when the user starts writing. `chat.models` returns the space's models and its `default`.
- F29. `session.prompt` with the `id` of a message the session has (in its inbox or its history) admits nothing and returns the stored item (`{ id, type: "user", payload: { text, … } }`, the stored text, not the new one); with `resume` other than `false` it still wakes the session, which runs no step when nothing is pending _(run)_. `session.prompt` with `metadata` keeps it, and `ctx.session.context` returns it on the user message _(run)_.
- F30. `session.viewed` is published only when a client acknowledges an unread idle session (`Session.view`, which the TUI calls for the focused unread session); it is not a signal that a session is open.
- F31. A Chat API client sees a user message's sender as `sender.userId` only: the `userName` the brain stamps in the OpenCode metadata is not translated (`opencode-transcript` `withMetadata`). The origins (`channel`, `schedule`, `webhook`, `task`) are on the message (`session.message`, `session.messages`), not on `session.inbox.enqueued`, whose payload has only the prompt fields and `sender`. `me.get` returns the signed-in user's ID, which is the `sender.userId` of their messages; `space-member.list` with `spaceId` lists the space's members with their names and ignores `userId`.
- F32. An open Chat API event stream holds the brain's harness (`Cell.acquire`), so the alarm does not close it. The brain ends the stream with `stream.ended` `idle` after `CHAT_IDLE_MS` (2 minutes) without events while no session of the brain is active, and `Connection` parks on it until something wakes it; the web app wakes on focus, network and typing.
- F33. On a real brain, a teammate's steer sent through the Chat API during a step of another member's execution is delivered after that step's `session.step.ended` and answered by the next step of the same execution _(run)_.
- F34r. In 2.2.6, `session.update({ title })` (the TUI's `/rename`, which trims and ignores an empty title) publishes `session.renamed` with `{ sessionID, title }`, and `ctx.event.subscribe({ types: ["session.renamed"] })` delivers it to the plugin of the session's location _(run)_. OpenCode's title generation publishes the same event: it shortens the `title` hook's result to 100 characters (97 and `...`), and it publishes nothing when the title changed during the generation. An HTTP `session.update` with `title: ""` generates the title again through the `title` hook _(run)_. An untitled 2.2.6 session has no `title` (the timestamped placeholder is only for display), so it publishes no placeholder.
- F35r. `session.rename` is on the Chat API only and needs a live brain. The brain publishes `session.renamed` on its Chat API stream for a rename from any client and from the brain itself _(run)_. Chat API `session.get` returns the brain's current title, with no `title` while untitled. Ren's `session.get` has the title only after the next sync. `session.create` takes no title.
- F34c. OpenCode 2.2.6 has no `fork` session hook (2.3.0 adds one). A fork publishes `session.forked` (`sessionID` is the fork, `parentID` the source); the fork copies the source's model, metadata and messages under new message IDs, and its `Session.Info.fork` names the source. A plugin's `ctx.event.subscribe` sees `session.forked`, `session.model.selected`, `session.archived`, `session.unarchived` and `session.deleted` _(run)_, only for sessions of its own location (the bus filters typed subscriptions by location). `session.update` with `metadata` replaces the metadata _(run)_.
- F35c. The 2.2.6 TUI keeps a picked model as a draft and commits it with `session.switchModel` right before each prompt or command it sends (read in its source, not run). `session.model.selected` carries `previous`; switching to the current model publishes nothing; `session.context` returns `model-switched` messages with `model` and `previous`. The `prompt` hook runs before the prompt is admitted and before its step reads the session's model, and `ctx.session.switchModel` and `ctx.session.synthetic` work inside it, so a switch made in the hook applies to that prompt's step _(run)_. Session hooks cannot fail (their failure type is `never`).
- F36c. A `compaction` hook `result` with `summary` makes OpenCode store a completed compaction with that summary and call no model. Afterwards `session.context` starts at the compaction: earlier messages are not returned _(run)_. Without a `result` the compaction calls the model with kind `compaction`, after the `model.request` hook. The compaction runs on the `compaction` agent's model when one is configured, so the plugin registers the hook for every provider and checks the binding.
- F37c. A real brain's Chat API `session.get` reports a model without a variant as `variant: "default"`; `session.model.switch` sets the model of the next step, and the model call uses it _(run)_. The brain's compaction message has the `id` sent to `session.compact`, so `session.message` finds it after a reconnect _(run)_.
- F34s. Ren's OAuth server (Better Auth `@better-auth/oauth-provider` 1.7.7) binds a refresh token to the client that got it: the refresh grant answers `invalid_grant` when `client_id` differs (`refreshToken.clientId !== client_id`), and revocation checks the client too. Reusing a rotated refresh token after a short reuse window revokes the whole family (`invalidateRefreshFamily`). The consent page names the client by its metadata's `client_name` (`packages/app` `consent-page.tsx`); the CLI's is "Ren CLI", served by the server itself (`ClientMetadataFetch`). A login the plugin got as the CLI's client is renewed by `ren` and the other way round _(run, e2e)_.
- F35s. The TUI plugin context of 2.2.6 has no helper to open a URL or to copy text (OpenCode's own dialogs use an internal `openUrl` and clipboard). The TUI part runs in Bun, so it spawns `open` or `xdg-open` itself. `ui.dialog.prompt` shows a wrapped `description`, returns the typed text or `undefined` on escape, and closes with `ui.dialog.clear()`; `ui.dialog.confirm` returns a boolean _(TUI)_.
- F36s. A plugin can add an OAuth method to an integration (`ctx.integration.transform`, `editor.method.update({ integrationID, method: { id, type: "oauth", label }, authorize })`); OpenCode's `/connect` dialog then opens the URL, offers copy and paste of the redirect, polls the attempt and stores the `Credential.OAuth` the callback returns (`access`, `refresh`, `expires`) in OpenCode's credential store, which refreshes it with the method's `refresh`. An `external` method records a reference and runs no flow (`claude-agent`'s `integration.ts`).
- F37s. The Promise RPC client's `events.on` filters by event type and drops `server.connected`, so a caller cannot see when its subscription is live; every subscription of one client shares its event connection. A sign-in's outcome arrives after a browser round trip, long after the TUI subscribed.
- F34b. OpenCode's plugin runtime (`ensurePluginRuntime`, which the CLI and the TUI call at start) serves `effect`, every public `effect/*` subpath and every `@opencode/plugin` entrypoint to plugins from the host's copy, also to imports from a plugin's `node_modules`, and refuses to load files of a plugin's own copy of either. A bundle that keeps them external, alone in a `node_modules` folder with nothing to resolve them from, loads and runs a turn _(run, in-process and in the stock 2.2.6 binary)_.
- F35b. The TUI's Solid transform (`@opentui/solid` 0.8.1 `createSolidTransformPlugin`, installed by `ensureRuntimePluginSupport`) compiles only files outside `node_modules`; an installed package's `.tsx` would load with Bun's default JSX. OpenTUI's runtime plugin rewrites `@opentui/*`, `solid-js`, `solid-js/store` and `@opencode/plugin/tui` imports in a `node_modules` ESM file to the TUI's instances, and leaves the specifiers OpenCode's runtime provides. So the published TUI part is JavaScript compiled with the same Solid transform; it loads and works from a `node_modules` folder in the stock 2.2.6 TUI (footers, `/ren:space`) _(TUI)_.
- F36b. `opencode plugin add` installs a package with npm Arborist into OpenCode's cache, which installs required peer dependencies; `@opencode/plugin` marks its own TUI peers optional. `Host.resolve` resolves a directory whose `package.json` has `name` and `exports` through the package name, as for an installed package.
- F37b. `ctx.app.version` (server) and `context.app.version` (TUI) are the host's version: the release `X.Y.Z` in the stock binary, `local` in a source build, `0.0.0-<channel>-<n>` in dev and beta builds, and `unknown` in an embedded host unless it passes `app` (`createEmbeddedRoutes`). OpenCode 2.2.6 is the first release with `effect` 4.1.0 (2.2.2 to 2.2.5 ship 4.0.6); 2.3.0 to 2.3.2 also ship 4.1.0, `@opentui/*` 0.8.4 and `solid-js` 1.9.17.
- F34m. In 2.2.6 only the TUI part can export a session: `context.client.experimental.session.export({ sessionID })` returns OpenCode's `SessionTransfer.Data` (`{ info, messages }`) as its HTTP API encodes it, with unfinished assistant, shell and compaction messages left out. A server part's `ctx.session` has `context`, which lacks the full messages, and no export _(run)_.
- F35m. An RPC call from the Promise client carries a 32 MiB input to the server part _(run)_.
- F36m. Ren's `session.import` (`POST /sessions/:id/import`, hidden from Ren MCP) takes `{ spaceId, harness: "opencode", model?, transcript }`, with a body of at most 32 MiB (`Session.maxImportBytes`; other routes keep 1 MiB). `opencode-transcript` decodes the export with OpenCode's own schema (`Schema.toCodecJson(SessionTransfer.Data)`) and writes the rows OpenCode's import writes; a recorded chat's export gives back its message rows unchanged _(run)_. The chat gets `origin: "opencode"` and the local title, and the start restores the rows on the brain before it starts the chat _(run)_. The same person importing the same ID into the same space starts the brain again and changes nothing else; another space, another person or `session.create` with that ID is a conflict _(run)_.
- F37m. A restored chat whose last message is a user message with no answer: the next prompt starts an execution whose first step answers that message, and the new message is delivered after it and answered by the next step _(run)_.
- F38p. `ctx.permission.assert` called from a plugin's own fiber, outside any tool, creates a real pending request of the session: OpenCode publishes `permission.asked`, `session.permission.list` and `reply` see it, and the stock TUI shows its own prompt for a request of the session or a descendant _(run, TUI)_. It evaluates the local rules first. A deny rule of the session's agent or the session fails it at once with a `Tool.Error` whose `error` is the `Permission.BlockedError`, before the hook (read in source). The rules allow without asking when they match, and the default agent's rules in the test host do; the `evaluate` hook runs after them and can set `effect: "ask"`, which then asks _(run)_. The plugin's input has no `id`, so the local request has its own ID; `permission.asked` carries the metadata the plugin passed, which finds it _(run)_. It succeeds for `once` and `always` alike; `permission.replied` carries the `reply` _(run)_. A plain rejection is a defect (`Permission.DeclinedError`; read in source), which the plugin's own fiber catches as a rejection _(run)_; a rejection with a message is a `Tool.Error` whose `error` is the `Permission.CorrectedError` and whose `message` is the feedback _(run)_. A rejection also rejects every other pending request of the same session, and `always` stores the `save` patterns as saved rules of the local project (read in source). HTTP has `session.permission.create` too (not used).
- F39p. A server plugin has no form API. OpenCode 2.2.6's HTTP API has `session.form.create` with a chosen `id` (a second create with that `id` fails with `ConflictError`), and the TUI part's `context.client` reaches it; Ren's `Form.ID` and fields are OpenCode's. The stock TUI shows a pending form of the session or a descendant with its own form UI, several fields as tabs and a review before submit _(TUI)_. `form.replied` and `form.cancelled` reach a server plugin's `ctx.event.subscribe` _(run)_. Pending forms live in the memory of the OpenCode process. The Promise client rejects with the tagged error object (`{ _tag: "ConflictError", … }`, `FormAlreadySettledError`), not `{ type, message }` as for RPC _(run)_.
- F40p. The stock 2.2.6 TUI offers "Always allow" only when the request has `save`, and then lists the `save` patterns _(TUI)_; it asks for a rejection message only in a subagent session (one with `parentID`), and in its `autoaccept` permission mode itself replies `once` to every request of the session family (read in TUI source).
- F41p. On a real brain, a permission request and a question of a remote turn reach the local session through the mirror, and the local answer lets the remote turn go on and finish in the same local step _(run)_. For a question the brain already cancelled, the plugin treats `NotFoundError` and `ConflictError` from `session.form.reply` as gone, as the web app's `replyForm` does (not run on a real brain).
- F38o. In 2.2.6 a server plugin's `ctx.session` has no import and no inbox (`SessionDomain` picks `list`, `create`, `get`, `remove`, `prompt`, `synthetic`, `update`, `context` and a few more); the TUI part's `context.client` has `experimental.session.import` and `session.inbox.list`. The import validates each message against OpenCode's message schema, drops unsettled messages (a running assistant, shell or compaction), resolves the project from `location` and ignores `info.projectID`, and needs `info.cost`, `info.tokens`, `info.time.created`, `info.time.updated` and `info.location` _(run)_. It publishes only `session.created`: no `session.renamed` and no `session.model.selected` _(run)_.
- F39o. A Chat API message is OpenCode's message with Ren fields lifted out of `metadata`; tool parts keep `state.metadata`. Converted back (user metadata from `sender` and the mirror's naming, `ren` model refs, text parts without `time`, compactions without `recent`) and imported, a real brain's transcript with a subagent tool call reads back with the same message IDs and the tool's metadata (`sessionID`, `status`, `truncated`) _(run)_. The brain's tools in `BrainTest` are `question`, `skill`, `subagent`, `webfetch`, `websearch` and `execute`. Ren API `chat.messages` returns the same types, newest first; the Chat API path is `/chat/session/:id/message`.
- F40o. A prompt with `resume: false` into an idle session stays in its inbox (`session.inbox.list`) and is not in `session.context` _(run)_. Removing the session discards it, so a refresh asks the TUI for the inbox first.
- F41o. The 2.2.6 TUI, on `session.deleted` of the session it shows, navigates home and shows "The current session was deleted"; tabs close. On `session.created` its data layer marks the session's messages as loaded and empty (`sync.complete("session.message:<id>")`, read in `@opencode/client/solid` `data.ts`), so an imported session shows no messages until a plugin calls `data.session.message.invalidate` and `sync` _(TUI)_. `ui.router.current()` and `data.session.status()` are reactive. A select dialog's footer `actions` run without closing it, and a new `ui.dialog.select` replaces the open dialog, resolving the old one with `undefined` _(TUI)_. The select `search` is synchronous over the given options, so it cannot ask a server.
- F38a. A stored user message holds its prompt's files with their bytes, read when OpenCode admitted it (`SessionPrompt.prepare` in 2.2.6): `{ data (base64), mime, source, name, description, mention }`. OpenCode read a `file://` file (at most 20 MiB, else the prompt is refused), cut a `?start=&end=` range of a `text/plain` file to those lines, turned a folder into its listing with mime `application/x-directory`, decoded a `data:` URI, re-read a `media:` ref and shrank an image. A missing file fails the prompt at admission, before any turn. `ctx.session.context` returns the files with `data` _(run)_, so the plugin reads no local file. Skills are stored as `{ id, name, text, mention }` with the skill's prepared text; agents as `{ name, mention }`. The local model gets the skill texts, then the text, then `text/plain` files and folders as text and PNG, JPEG, GIF, WebP and PDF as media, and nothing of other types or of agent attachments (`to-llm-message.ts`). A TUI skill mention's ID is the skill's name.
- F39a. Chat API `session.prompt` takes drive files only (`{ path, name }`, at most `Session.maxDriveFiles`, 10); inline `data:` files are on Ren's API only. The brain's chat reads drive files on its hand (`DriveFiles.attach` in `@ren/brain`): it types a file by its path's extension (`Drive.typeOf`) and gives the model text, JSON, readable images and PDFs inline up to `Session.inlineLimitOf`, others by path. A brain whose chat cannot read the space's drive refuses the prompt with "This chat cannot use the space’s drive." _(run, `BrainTest`)_. Ren's `agent.list` and `skill.list` are the brain OpenCode's agents and skills; a passed agent is stored on the brain's message _(run)_. The Chat API client sends unset optional prompt fields as JSON `null`.
- F40a. A plugin adds a command with `ctx.command.transform` (`editor.add({ name, description, execute({ sessionID, prompt, delivery }) })`). Chat API `command.list` is per Ren session and needs its brain running, and `session.command` admits the command's message under an ID the brain picks, so a local session sees its turn only through the mirror (read, not run).

- F38t. Ren's `chat.access` (core `Brains.access`, `MachineLifecycle.access`) answers `stopped` for a stopped brain and does not start it, answers `failed` for a failed brain until its retry time, and starts a sleeping or paused brain (`ensure`) and answers `starting`. So a client that asks for access wakes the brain, and Ren bills it. Only new work or `chat.retry` starts a stopped brain. `chat.retry` restarts the brain; its `message` is used only for a session that never reached its brain. The web app calls `chat.retry` without a message and then sends its unsent messages again with their IDs (`ChatSession.retry`, `host.ts` `restart`). `@ren/client` sends it as `{"message":null}` _(run)_.
- F39t. `ChatAccess.client` asks Ren every 2 seconds, without a limit, while Ren answers `starting`. So a first start never reached the turn's former one-minute wait for a connected stream, but a reconnect whose new access said `starting` did, because the wait counted from before that access _(run, `TestClock`)_. A link keeps `failed` and `stopped` for its life: its `client` fails and its stream parks.
- F40t. In 2.2.6, a prompt to a session whose `ren/*` model is no longer registered (after `/ren:logout` the plugin lists no models) ends at once with an idle outcome `failed`, `provider.no-route` "Model unavailable: ren/<model>", and the plugin's model never runs _(run)_. A login that expires and that Ren does not renew reaches the plugin's model until the next model refresh (at most 5 minutes) _(run)_.
- F41t. `ctx.session.synthetic` with `resume: true` admits a synthetic message and runs a step on the session's model, while `session.prompt` with an ID the session has runs no step (F29) _(run)_. The 2.2.6 TUI has no command that retries a failed turn. Its notifications plugin (`feature-plugins/system/notifications.ts`) notifies "Session done" at every local `session.execution.succeeded` or `interrupted`, and notifies and shows a toast at `session.execution.failed`, with the notification only while the terminal is not focused.
- F42t. The TUI slots `prompt.footer.status` and `prompt.footer` get an optional `sessionID`; `session.composer.top`, `sidebar.content` and `sidebar.footer` get one always; `home.footer.status` gets none (`@opencode/plugin/tui` 2.2.6 `SlotMap`).

- F38n. A plugin's session panel (`ui.panel.open(name)` with a `session.panel` slot that renders by `panel.name`) opens only in a session and takes the input when it opens; its keymap layers (inline commands with `bind`, created in the panel's component) work only while it owns the input, and OpenCode's `<leader>left` and `<leader>right` (`pane.focus.left`, `pane.focus.right`) move the input between the session and the panel _(TUI)_. OpenTUI's `<diff>` (unified, with the theme's `diff` tokens) and `<code>` render with a plugin's `SyntaxStyle.fromStyles(…, context.renderer.nativeScene)`, and tree-sitter colours TypeScript in them _(TUI)_. `<code>` with `filetype` `markdown` hides the markup unless `conceal={false}` _(TUI)_. OpenCode's own diff viewer (`DiffViewerContent`, `PatchDiff`) is internal to the TUI, not plugin API.
- F39n. A VCS provider (`ctx.vcs.transform`, `VcsDefinition`) gets only a `VcsScope` (`directory`, `worktree`, `canonical`, `store`), no session, and its selection (`default.set`) is per location (2.2.6 types). A local Ren session's location is the user's directory, so a provider for Ren would replace git for every local session there. The built-in `/diff` on a Ren session shows this machine's git. The shell hook `create.before` gets `command`, `cwd`, `timeout`, `shell` and `env`, no session, and the command still runs on this machine, so `!` stays local.
- F40n. On a real brain with a hand (`BrainTest.make({ hand: true })`, a `TestHand` executor), Chat API `file.list`, `file.read`, `vcs.projects`, `vcs.get`, `vcs.diff` (`working` lists a file nobody added as `added`) and `shell.create`, `shell.get`, `shell.output` work, and a file that the brain's `shell` tool wrote is listed, read and diffed _(run)_. Without an environment the brain refuses them with `InvalidRequestError` "Session … has no environment". `file.list` entries from a hand carry no `size`. After `shell.remove`, `shell.get` and `shell.output` answer `NotFoundError` (the protocol's description: the output is dropped).
- F41n. A hand whose folder path goes through a symlink (macOS `/var` → `/private/var`) lists files but `file.read` answers `NotFoundError` for them; with the real path both work _(run)_. Ren's hands use `/workspace`, so this concerns tests; `BrainTest`'s hand uses the real path.
- F42n. Opening a link starts its event stream (`Connection.make` subscribes at once), and a link that no scope holds is closed, so its `chat.access` is asked again at the next open: two panel calls in a row ask `chat.access` twice _(run)_.
- F43i. No Ren endpoint returns the web app's address: the server's `APP_URL` is configuration only, used in its emails, the OAuth login and consent pages and channel redirects. The mobile app uses `EXPO_PUBLIC_REN_APP_URL`, default `https://useren.ai`; the server is `https://api.useren.ai`, and in development the API is on port 4000 and the app on 5173 (`.env.example`, `CONTRIBUTING.md`). The app's pages are `/sessions/:id`, `/spaces/:idOrSlug` and `/tasks/:id`.
- F44i. Ren's API has no context window for a session: `chat.models` returns `SessionModel.Choices`, without `limit`; the limit (`SessionModel.Info`) is on the Chat API's `model.list`, which needs a running brain. The web app's context ring reads the newest step's tokens from the live chat state. Ren's `chat.messages` returns the assistant messages with `tokens` _(run against the fake Ren only)_.
- F45i. The 2.2.6 TUI renders a plugin's `sidebar.content` claim in a session's sidebar after the built-in sections, with the session's `sessionID`, and re-renders it reactively _(TUI)_. OpenTUI 0.8.1's Solid catalogue has `<a href>` (a span with a terminal hyperlink) inside `<text>`; it renders its text _(TUI)_; whether a click opens it depends on the terminal (not run). `ui.dialog.alert` exists in 2.2.6 (types).

## 4. Features, in build order

Each is one commit. Built features leave the list; the others keep their numbers.

- **11a. Ren commands.** List the Ren session's server commands (`command.list`) as local commands and run one with `session.command`, its turn shown through the mirror; on a session that is not a Ren session, say that they work only there. Not built with feature 11: the list is per Ren session and needs its brain running, while OpenCode's command list is one per location and changes only on `command.reload`, and the command's message gets an ID the brain picks, so its turn depends on the mirror (F40a, L12).
- **15a. Background and activity.** `/ren:background` calls `session.background` for the current Ren session while a blocking activity runs (the web app's Ctrl+B, `use-chat.ts`), and an activity panel lists the running shells (`shell.list`, which the shell panel already reads) and subagents (`session.children` with `session.status`) with stop (`shell.remove`, `session.interrupt` on the child). Reuse `Hand` (one link per call) and the `session.panel` slot.

## 5. Limits

- L1. Edit diffs and subagent links show as generic tool rows (F5). A fix needs proxy tools that wait for the remote result, limited to Ren sessions, or an OpenCode change.
- L2. Sender names are a text prefix (F10).
- L3. `@` file search and `!` shell are local (F11). The browser tab is not possible in a terminal.
- L4. Undo and redo: only user message IDs match between local and Ren.
- L5. A queue is local until sent. Other users do not see it.
- L6. Cost is the catalog price (F8).
- L7. Models and server commands are one list for all spaces; the plugin checks the selection at send time. A model that a Ren session's space does not offer fails its turn with Ren's reason when the plugin switches the brain to it. Each location loads its own server part (`ctx.location`), so a server part in another directory is expected to list a newly selected space's models only at its next refresh, within 5 minutes (not run).
- L11. `/ren:space` lists the first 100 joined spaces.
- L8. Presence and fork do not exist in Ren (F14).
- L9. Events lost while the event stream reconnects mid-turn are not replayed into the local message; the turn goes on with the next events, or finishes when the brain is idle. Catch-up does not notice them while the copy shows an answer for that turn (L22o).
- L12. The mirror shows a message from another client only while the Ren session is watched: from a local turn in this OpenCode process until the brain's idle end of the event stream (F32), at most 4 sessions. A remote turn already running when a session is opened, and messages delivered while it was not watched or while the event stream reconnected, are not shown live; catch-up imports them when the TUI shows the session again or it goes idle (L24o).
- L13. A step of the local session ends at the delivery of another user message, so two messages delivered back to back can leave one local step empty. A synthetic continuation (a subagent's result, a scheduled wake) streams inside the running step, or not at all when no step runs.
- L14. A local prompt during a mirrored turn waits until that step ends (F4), so the local user cannot steer a teammate's running turn from OpenCode.
- L15. Names come from the space's member list, because the Chat API does not expose the `userName` the brain stamps (F31); a channel, schedule, webhook or task message shows its origin.
- L16r. A rename on Ren shows locally only while the session is watched, or at its next connect, which reads the brain's title (L12). A local rename that does not reach the brain within a minute (stopped, failed, unreachable, signed out) stays local and is sent at the session's next connect in this OpenCode process; a restart forgets it, and the brain's title then wins. A Ren rename that arrives while a local rename is on its way is dropped. With the capability `rename` false, a local rename stays local.
- L16c. A switch of a Ren session to a local model is undone, not prevented (OpenCode has no veto, F35c). A prompt never runs on the local model, but a step that an already running execution starts between the switch and the revert can. The plugin tells the user with a notice (a synthetic message), because a server plugin cannot show a toast.
- L17c. A compaction that another client or the brain starts on Ren is not shown in the local session. When a `compaction` agent model is configured to a local model and Ren refuses a compaction, OpenCode summarizes the local history with that model.
- L18c. Ren has no unarchive (F14): unarchiving a local Ren session leaves the Ren session archived, with a notice. Deleting a local copy never changes the Ren session.
- L19c. A fork of a Ren session is local only (F14): it is disconnected from Ren, and its `ren/*` model refuses to run until the user picks a local model.
- L16s. The consent page says "Ren CLI": the plugin signs in as the CLI's client, because the two tools renew one stored login and a refresh token works only for the client that got it (F34s). A client of its own would need a hosted client metadata document, an entry in the server's `ClientMetadataFetch`, and the client recorded with each login in the shared file, which changes the CLI's format.
- L17s. Ren is not an integration in OpenCode's `/connect`: an OAuth method's credential is a second copy of the refresh token in OpenCode's store (F36s), and the two copies cannot both stay valid when either side rotates it (F34s). `/ren:login` shows its own dialog instead.
- L18s. When the server part runs on another machine than the TUI, the browser's redirect to `127.0.0.1` reaches nothing; the user pastes the address from the browser into the sign-in dialog (run with the fake Ren, in tests and by hand in the TUI).
- L19s. After `/ren:logout`, a Ren session's open Chat API connection keeps working until its chat token needs renewing (at most 60 minutes, F13).
- L16b. The supported range is `>=2.2.6 <2.4.0`; 2.3.x is covered by a typecheck of the source against `@opencode/plugin` 2.3.2 only, not run. The published `./rpc` has no type declarations.
- L16m. A move takes the root session only: subagent sessions, fork lineage and a staged revert stay local, and OpenCode's export leaves out unfinished messages (F34m). The moved history's tool calls refer to the local machine's files; the brain continues on its hand, so the repository must be reachable in the space.
- L17m. A session over 32 MiB as exported does not move (F36m).
- L18m. A model change from a local model to `ren/<model>` does not move a session: one with a finished local answer is refused at its next prompt with a message to run `/ren:move` (F34m: the server part, where the turn runs, cannot export).
- L19m. The brain restores a moved chat in the folder Ren gives it on its hand (`sync.restore` `directory`). When Ren gives none, as for a brain without environment connections, the chat keeps the local folder path, where its tools find nothing (not run on a hand).
- L20p. A request shows locally only while the Ren session is watched (L12) or at its next connect, which lists the pending ones. A question needs a TUI part: the server part has no form API (F39p), so with no TUI connected (for example `opencode serve` with another client) a question shows when a TUI connects.
- L21p. Local rules: a local deny rule for the request's action keeps the request from showing (the plugin logs a warning; answer it in another Ren client). "Always allow" stores the `save` patterns, with ` (on Ren)` appended so they match no local resource, as saved rules of the local project. The stock TUI's `autoaccept` mode approves Ren requests once (F40p).
- L22p. A subagent's request shows on the local root session, so the stock TUI never asks for a rejection message (F40p), and a local rejection also rejects the other pending Ren requests of that local session, including other subagents' (F38p). Other clients of OpenCode's HTTP API can send a message.
- L20o. Opening imports the root session only. Subagent child sessions are on the Chat API only (a live brain), so a subagent tool row's link names a session that is not local.
- L21o. An imported copy is lossy where the Chat API is: message `metadata` other than the sender and origins, text and reasoning `native` replay data, text part times, and drive uploads of user messages (only their text shows). Every imported user message is `remote: true`, so `doStream` never sends it. The copy's cost and tokens start at 0.
- L22o. The catch-up comparison reads Ren's newest 20 saved messages: a copy is behind when, after the newest message both have, Ren has a user, synthetic or compaction message the copy lacks, or an answer while the copy has none. It does not notice parts missing inside a turn the copy shows (L9) or shell, skill and system messages. A copy whose newest shared message is older than those 20 counts as behind.
- L23o. A refresh removes the copy and imports it again: the TUI shows home and "The current session was deleted" for a moment, then the session again (not tried with tabs on). Local-only rows are dropped: plugin notices, failed local turns, local model switches and the local compaction row (Ren's replaces it). A refresh is skipped, with a notice, while a local turn runs, while the inbox holds items, or while the copy has user messages after its last answer that Ren lacks. If the import fails after the removal, the copy is gone until `/ren:sessions` opens it again.
- L24o. Catch-up runs only in a TUI (a server plugin cannot import, F38o): for the session the TUI shows, when it shows it and each time it goes idle, and from `/ren:sessions`. A turn running on Ren when the copy is imported shows at the next catch-up. Catch-up reads Ren's saved copy, which can lag the brain (not measured); it then finds no difference or skips, never loses local messages. Automatic catch-up fails silently and watches the session, which wakes its brain.
- L25o. The transcript goes from the server part to the TUI in one RPC response (32 MiB, measured by the move feature, not here), so a larger session cannot be opened.
- L26o. `/ren:sessions` lists one page of 50 sessions. Typing filters those rows; Ren's text search is the `ctrl+f` action, because the TUI's select search is synchronous (F41o).
- L20a. A message's files go through the space's drive. A brain whose chat cannot read the drive refuses a message with files, and the turn fails with its reason. At most 10 files a message, skill files included (F39a).
- L21a. The brain types a file by its name, so the plugin renames some: a pasted image gets the extension of its type, a text file without a text extension gets `.txt`, a folder's listing is `<name>.listing.txt`, and a second file with the same name gets ` (2)`. The brain's model does not get the local path that a local model gets for an image, a PDF or a folder.
- L22a. Only `@` mentions that the TUI turned into attachments are sent as files; a typed `@path` stays text, and the brain reads it as a path on its hand (L3). An agent mention the brain does not list is left out; a skill the brain does not list goes as `<name>.skill.md` with its text. The agent picked in the TUI does not change the Ren session's agent. No `presentation` is sent: OpenCode keeps no display form of a message.
- L23a. `ren` models declare text input only, because Ren lists no modalities. The TUI attaches images and PDFs anyway; OpenCode's web and desktop composers decide by the model's input (read, not run).
- L20t. A status read never asks Ren for chat access (F38t). A session without an open link (no turn here since the OpenCode process started, or no longer watched) shows only its space; a stopped or failed brain shows once a turn opens the link. `/ren:retry` on such a session runs the turn again, which fails with Ren's reason, and a second `/ren:retry` starts the brain again.
- L21t. `Working` comes from the execution events since the event stream connected: an execution already running at a connect shows as idle until its end.
- L22t. The footer shows `Signed out` only when the stored login is gone or Ren refused to renew it. A login that Ren revokes before it expires fails turns with "Run /ren:login" (Ren answers 401 to `chat.access`; not run), while the footer shows the reconnecting link. After `/ren:logout`, a prompt fails with OpenCode's "Model unavailable" (F40t).
- L23t. `/ren:retry` after a turn that failed on the brain sends the text again as a new message, so the local session shows it twice (the web app's "Try again" does the same). Whether Ren has the message is read from Ren's saved messages (`chat.messages`, the newest 20), which the brain syncs to Ren with a delay.
- L24t. No notifications are added: OpenCode already notifies the end and failure of every local execution, which includes mirrored remote turns and turns that waited for a long start (F41t). A remote turn the mirror does not show is not known.
- L25t. The footer and the `/ren:retry` keymap entry were not run in the stock TUI; `RenCommands.retry`, `sessionStatus` and `describe` run in tests against a real OpenCode. The `/compact` wait (`Controls`) keeps its one-minute limit for a starting brain.
- L20n. The panels refresh on demand (`r`) and the shell panel polls its command's output every second; nothing follows `shell.created` or `shell.exited`. Each call opens the session's link, with an event stream and usually a `chat.access`, and lets it go. A panel's lists scroll with the keyboard only.
- L21n. Panel bounds: a patch at 64 KiB, a diff at 512 KiB, a file at 256 KiB (Ren's own read limit is 1 MiB), 50 search results, 64 KiB of output per read and the last 256 KiB in the shell panel. A cut patch can end inside a hunk. Binary files are not shown.
- L22n. `branch` and `committed` compare with the base the hand's git finds; the panel has no base picker. A session created with `/ren:new` has no panels until its first prompt creates the Ren session.
- L26i. The web app's address is not on Ren's API (F43i): the plugin derives it from the server URL (`api.` dropped, `localhost:4000` to `localhost:5173`, else the server's origin), and a server laid out otherwise needs the plugin option `appUrl`.
- L27i. The sidebar's context is a token count without a percentage (F44i), from Ren's newest 20 saved messages, which lag the brain; the cost comes from Ren's usage events, which arrive seconds after each call and leave out what the organization pays with its own key. A link added by another client shows at the next refresh: when the session is shown again, after a local turn, at a status change, a sign-in or sign-out, or a reconnect. Each refresh makes up to six Ren API calls, and one reads GitHub when the session has pull requests.
- L28i. A link in the sidebar is a terminal hyperlink only where the terminal supports one (not run); `/ren:links` opens them everywhere. The opener is `open` or `xdg-open` on the TUI's machine; without one a dialog shows the address.
