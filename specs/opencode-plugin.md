# OpenCode plugin (`@renai-labs/opencode`)

The plugin makes a user's own OpenCode a Ren client. Local OpenCode sessions keep working beside Ren sessions in the same TUI. The package is `packages/opencode`; its `README.md` and `AGENTS.md` hold what is built and the package rules. This spec holds the plan. Remove a part from here in the change that builds it.

## 1. Decisions

- D1. **Ren as a provider.** The server part registers a provider `ren`. Its language model is an AI SDK `LanguageModelV3` in plugin code, as OpenCode's `claude-agent` provider is. One `doStream` sends the prompt to the brain of the Ren session through the Chat API and streams the remote turn into the local session. The brain runs the tools; the stream reports them as executed by the provider.
- D2. **A Ren session is a local session with a `ren/<model>` model and the metadata `ren: { spaceId, sessionId }`.** The local session ID and the Ren session ID are the same ID.
- D3. **The plugin never selects a brain.** For each Ren root session it calls `chat.access(sessionId)` and gets a URL and a token. Every brain and hand layout works the same way. The plugin enables features from `Session.Capabilities`, not from the layout.
- D4. **Three parts:** the server part (`@opencode/plugin/effect`), the TUI part (`@opencode/plugin/tui`) and the RPC contract between them (`@opencode/plugin/rpc`).
- D5. **Stock OpenCode only.** No patched OpenCode. `effect` and `@opencode/plugin` come from the host.
- D6. **Commands are `/ren:<command>`.** Built-in commands keep their names and act on Ren sessions through hooks and events.
- D7. **Published alone.** The build bundles `@ren/client`, `@ren/chat`, `@ren/schema` and `@ren/protocol`.
- D8. **Each feature is one commit with its tests.** Write the test first. Add an end-to-end test where a real brain and a real OpenCode host can run.

## 2. Facts the design depends on

Read in OpenCode 2.3.0 source (the dependency is 2.2.6) and Ren. Facts marked _(run)_ were run on 2.2.6 by the plugin's tests, which host OpenCode in-process with the plugin loaded from its directory. Facts marked _(TUI)_ were run by hand in the stock OpenCode 2.2.6 TUI (`opencode --standalone` with isolated `XDG_*` directories and the fake Ren of `test/lib/ren.ts`); no test runs the TUI, because OpenCode does not publish it.

- F1. A plugin cannot write assistant messages or tool parts into a session. The model stream is the only path. `session.prompt` (with `id`, `metadata`, `resume`) admits a real user message.
- F2. The runner gives each model request the header `x-opencode-session-id`, and it reaches `doStream`. The `model.request` hook gets `sessionID`, `kind` (`primary`, `compaction`, `title`, `generate`), `model` and mutable `headers`; a header it sets reaches `doStream` _(run)_. In 2.2.6 the `context` hook's messages carry the message `id` but not its stored `metadata` (2.3.0 adds that), and no type: `ctx.session.context` returns the stored messages with `type`, `id`, `text`, `metadata` and the assistant's `error` and `time.completed` _(run)_.
- F3. `doStream` gets no `abortSignal`. A stop cancels the returned `ReadableStream`; its `cancel` is the stop signal _(run)_.
- F4. A step whose tools are all provider-executed does not continue. One remote turn is one local step. A steer admitted during the step is delivered after it.
- F5. A provider-executed tool result keeps no `metadata`. The TUI's edit diff and subagent link read `metadata`, so those rows show as generic rows (limit L1).
- F6. A plain `Error` on the stream is retryable in OpenCode until the turn has produced output. A retry calls `doStream` again. The plugin's `retry` hook turns retries off for `ren`, as `claude-agent` does, because the brain retries model calls itself; a `doStream` can still run again for messages the brain has (a restart resumes the session), so the plugin asks the brain which messages it has before it sends, and sends with the local message ID as the prompt `id` _(run)_.
- F7. The `title` and `compaction` hooks accept a `result` that skips the model call (compaction _(run)_, F36c). `title`, `compaction` and `generate` requests reach the provider unless a hook supplies the result. A title `result` of `""` skips the model and keeps the session untitled, and OpenCode runs the title hook again at the next prompt while the session is untitled _(run)_.
- F8. Cost comes only from catalog prices of the model. The stream cannot report a cost.
- F9. `experimental.session.import` creates a session with a chosen ID, metadata and model. It cannot append. `session.remove` then import with the same ID is expected to work (not run).
- F10. The TUI user message shows text, files and skills only. It reads no metadata and has no slot.
- F11. The TUI composer's `@` file search and `!` shell act on the local machine. A plugin cannot add autocomplete sources.
- F12. A slash command name is split on white space (`parseSlashHead` in the 2.2.6 TUI), and a keymap command checks only that its ID is set, so `ren:space` is a valid name. A slash command without `arguments` runs from the completion list _(TUI)_.
- F13. Chat API events are not replayed on reconnect. After `server.connected` the client reads the resources again. A client token reaches only `/chat/*`, lasts 60 minutes, and carries the session ID; the brain sets the sender from the token.
- F14. Ren has no session import endpoint, no presence, no fork and no unarchive. `session.rename` is on the Chat API only.
- F15. _(run)_ An external plugin's `effect` runs with only `Scope` and the loggers in its context (`Plugin.load` in OpenCode's `packages/core/src/plugin.ts`). The plugin provides its own platform services: `FetchHttpClient` from `effect/http`, and Bun or `node:` APIs for files, because `effect`'s `FileSystem` needs a platform package that OpenCode does not provide to plugins.

- F16. `Provider.aisdk` is internal to OpenCode Core in 2.2.6 and not in `@opencode/plugin/effect`. A plugin's provider sets `package: "aisdk:<package>"`; the `sdk` hook's `event.package` is the name without the prefix, and the request's `providerOptions` key is the provider ID _(run)_.
- F17. A model ref with no chosen variant has `variant: "default"` in hooks _(run)_.
- F18. A model with `limit.context: 0` is never compacted automatically: the compaction ceiling of a window of 0 is infinite, and the output limit falls back to the catalog's _(run)_.
- F19. A plugin entry `{ "package": "<directory>", "options": { … } }` in `plugins` loads the server part from the directory's `exports` and passes the options as `ctx.options` _(run)_.
- F20. Brain event order, run on a real brain: a prompt to an idle session gives `session.inbox.enqueued`, `session.execution.started`, then `session.inbox.delivered` with `inboxID` equal to the prompt `id`, then the steps. A steer into a running execution is enqueued during the step, delivered after that step's `session.step.ended`, and answered by a new step of the same execution, which ends with `session.execution.succeeded`. So a local turn starts at the `delivered` of one of its messages and ends at the execution's end, or at the `delivered` of another user message once its own were delivered (F33, the mirror).
- F21. `session.create` with `message` gives the first message to the brain when it starts, before a client can open the event stream, so its delivery cannot be seen. The plugin creates the session without a message and sends the first message with Chat API `session.prompt` after it subscribed.
- F22. Effect's default `ConfigProvider` copies the environment at its first use, so the plugin reads `REN_URL` and `REN_TOKEN` once per OpenCode process. The credentials file is read on each request.
- F23. Plugin RPC: a method needs both `input` and `output` schemas; an RPC that a plugin did not register answers `rpc.unavailable`. The server decodes the input and encodes the output with the schema, and the Effect client decodes the output. The Promise client (`context.client` in the TUI) types only `Rpc.PortableDefinition` (Standard Schema or JSON Schema), returns the server's JSON without decoding it, and rejects with a plain `{ type, message, data? }` object. `Schema.toStandardSchemaV1` returns a value that is both an Effect schema and a Standard Schema, so one definition serves both clients when its schemas encode to themselves _(run)_. A declared error is `context.error(type, message, data)` returned as the handler's failure _(run)_.
- F24. RPC events reach every subscriber of the server as `rpc.<id>.<name>`; the event stream starts with `server.connected` once the subscription is live, so a test can wait for it before it acts _(run)_.
- F25. Plugin storage (`ctx.storage`) is OpenCode's global key-value table in its database, namespaced by plugin ID: one value for every location and process _(run)_.
- F26. `ctx.session.create` accepts `id`, `title`, `model`, `metadata`, `location` and `permissions`; a session created with a `ren/<model>` model and `metadata` keeps both _(run)_.
- F27. The TUI process installs the host's `effect` and `@opencode/plugin` for plugins (`ensurePluginRuntime`) and OpenTUI's Solid runtime plugin support, which compiles a plugin's `.tsx` and provides `solid-js` and `@opentui/*`. Importing the RPC contract with Effect schemas in the TUI part is safe _(TUI)_. `home.footer.status` and `prompt.footer.status` slots take JSX; `ui.dialog.select` marks `current`, takes `search`, and returns `undefined` on escape _(TUI)_.
- F28. Ren's web app creates a session at its first message and calls `chat.prepare` (which wakes a space's shared brain at most once per 5 minutes) when the user starts writing. `chat.models` returns the space's models and its `default`.
- F29. `session.prompt` with the `id` of a message the session has (in its inbox or its history) admits nothing and returns the stored item (`{ id, type: "user", payload: { text, … } }`, the stored text, not the new one); with `resume` other than `false` it still wakes the session, which runs no step when nothing is pending _(run)_. `session.prompt` with `metadata` keeps it, and `ctx.session.context` returns it on the user message _(run)_.
- F30. `session.viewed` is published only when a client acknowledges an unread idle session (`Session.view`, which the TUI calls for the focused unread session); it is not a signal that a session is open.
- F31. A Chat API client sees a user message's sender as `sender.userId` only: the `userName` the brain stamps in the OpenCode metadata is not translated (`opencode-transcript` `withMetadata`). The origins (`channel`, `schedule`, `webhook`, `task`) are on the message (`session.message`, `session.messages`), not on `session.inbox.enqueued`, whose payload has only the prompt fields and `sender`. `me.get` returns the signed-in user's ID, which is the `sender.userId` of their messages; `space-member.list` with `spaceId` lists the space's members with their names and ignores `userId`.
- F32. An open Chat API event stream holds the brain's harness (`Cell.acquire`), so the alarm does not close it. The brain ends the stream with `stream.ended` `idle` after `CHAT_IDLE_MS` (2 minutes) without events while no session of the brain is active, and `Connection` parks on it until something wakes it; the web app wakes on focus, network and typing.
- F33. On a real brain, a teammate's steer sent through the Chat API during a step of another member's execution is delivered after that step's `session.step.ended` and answered by the next step of the same execution _(run)_.
- F34r. In 2.2.6, `session.update({ title })` (the TUI's `/rename`, which trims and ignores an empty title) publishes `session.renamed` with `{ sessionID, title }`, and `ctx.event.subscribe({ types: ["session.renamed"] })` delivers it to the plugin of the session's location _(run)_. OpenCode's title generation publishes the same event: it shortens the `title` hook's result to 100 characters (97 and `...`), and it publishes nothing when the title changed during the generation. An HTTP `session.update` with `title: ""` generates the title again through the `title` hook _(run)_. An untitled 2.2.6 session has no `title` (the timestamped placeholder is only for display), so it publishes no placeholder.
- F35r. `session.rename` is on the Chat API only and needs a live brain. The brain publishes `session.renamed` on its Chat API stream for a rename from any client and from the brain itself _(run)_. Chat API `session.get` returns the brain's current title, with no `title` while untitled. Ren's `session.get` has the title only after the next sync. `session.create` takes no title.
- F34c. OpenCode 2.2.6 has no `fork` session hook (2.3.0 adds one). A fork publishes `session.forked` (`sessionID` is the fork, `parentID` the source); the fork copies the source's model, metadata and messages under new message IDs, and its `Session.Info.fork` names the source. A plugin's `ctx.event.subscribe` sees `session.forked`, `session.model.selected`, `session.archived`, `session.unarchived` and `session.deleted` _(run)_, only for sessions of its own location (the bus filters typed subscriptions by location). `session.update` with `metadata` replaces the metadata _(run)_.
- F35c. The 2.2.6 TUI keeps a picked model as a draft and commits it with `session.switchModel` right before each prompt or command it sends (read in its source, not run). `session.model.selected` carries `previous`; switching to the current model publishes nothing; `session.context` returns `model-switched` messages with `model` and `previous`. The `prompt` hook runs before the prompt is admitted and before its step reads the session's model, and `ctx.session.switchModel` and `ctx.session.synthetic` work inside it, so a switch made in the hook applies to that prompt's step _(run)_. Session hooks cannot fail (their failure type is `never`).
- F36c. A `compaction` hook `result` with `summary` makes OpenCode store a completed compaction with that summary and call no model. Afterwards `session.context` starts at the compaction: earlier messages are not returned _(run)_. Without a `result` the compaction calls the model with kind `compaction`, after the `model.request` hook. The compaction runs on the `compaction` agent's model when one is configured, so the plugin registers the hook for every provider and checks the binding.
- F37c. A real brain's Chat API `session.get` reports a model without a variant as `variant: "default"`; `session.model.switch` sets the model of the next step, and the model call uses it _(run)_. The brain's compaction message has the `id` sent to `session.compact`, so `session.message` finds it after a reconnect _(run)_.
- F34s. Ren's OAuth server (Better Auth `@better-auth/oauth-provider` 1.7.7) binds a refresh token to the client that got it: the refresh grant answers `invalid_grant` when `client_id` differs (`refreshToken.clientId !== client_id`), and revocation checks the client too. Reusing a rotated refresh token after a short reuse window revokes the whole family (`invalidateRefreshFamily`). The consent page names the client by its metadata's `client_name` (`packages/app` `consent-page.tsx`); the CLI's is "Ren CLI", served by the server itself (`ClientMetadataFetch`). A login the plugin got as the CLI's client is renewed by `ren` and the other way round _(run, e2e)_.
- F35s. The TUI plugin context of 2.2.6 has no helper to open a URL or to copy text (OpenCode's own dialogs use an internal `openUrl` and clipboard). The TUI part runs in Bun, so it spawns `open` or `xdg-open` itself. `ui.dialog.prompt` shows a wrapped `description`, returns the typed text or `undefined` on escape, and closes with `ui.dialog.clear()`; `ui.dialog.confirm` returns a boolean _(TUI)_.
- F36s. A plugin can add an OAuth method to an integration (`ctx.integration.transform`, `editor.method.update({ integrationID, method: { id, type: "oauth", label }, authorize })`); OpenCode's `/connect` dialog then opens the URL, offers copy and paste of the redirect, polls the attempt and stores the `Credential.OAuth` the callback returns (`access`, `refresh`, `expires`) in OpenCode's credential store, which refreshes it with the method's `refresh`. An `external` method records a reference and runs no flow (`claude-agent`'s `integration.ts`).
- F37s. The Promise RPC client's `events.on` filters by event type and drops `server.connected`, so a caller cannot see when its subscription is live; every subscription of one client shares its event connection. A sign-in's outcome arrives after a browser round trip, long after the TUI subscribed.
- F34b. OpenCode's plugin runtime (`ensurePluginRuntime`, which the CLI and the TUI call at start) serves `effect`, every public `effect/*` subpath and every `@opencode/plugin` entrypoint to plugins from the host's copy, also to imports from a plugin's `node_modules`, and refuses to load files of a plugin's own copy of either. A bundle that keeps them external, alone in a `node_modules` folder with nothing to resolve them from, loads and runs a turn _(run, in-process and in the stock 2.2.6 binary)_.
- F35b. The TUI's Solid transform (`@opentui/solid` 0.8.1 `createSolidTransformPlugin`, installed by `ensureRuntimePluginSupport`) compiles only files outside `node_modules`; an installed package's `.tsx` would load with Bun's default JSX. OpenTUI's runtime plugin rewrites `@opentui/*`, `solid-js`, `solid-js/store` and `@opencode/plugin/tui` imports in a `node_modules` ESM file to the TUI's instances, and leaves the specifiers OpenCode's runtime provides. So the published TUI part is JavaScript compiled with the same Solid transform; it loads and works from a `node_modules` folder in the stock 2.2.6 TUI (footers, `/ren:space`) _(TUI)_.
- F36b. `opencode plugin add` installs a package with npm Arborist into OpenCode's cache, which installs required peer dependencies; `@opencode/plugin` marks its own TUI peers optional. `Host.resolve` resolves a directory whose `package.json` has `name` and `exports` through the package name, as for an installed package.
- F37b. `ctx.app.version` (server) and `context.app.version` (TUI) are the host's version: the release `X.Y.Z` in the stock binary, `local` in a source build, `0.0.0-<channel>-<n>` in dev and beta builds, and `unknown` in an embedded host unless it passes `app` (`createEmbeddedRoutes`). OpenCode 2.2.6 is the first release with `effect` 4.1.0 (2.2.2 to 2.2.5 ship 4.0.6); 2.3.0 to 2.3.2 also ship 4.1.0, `@opentui/*` 0.8.4 and `solid-js` 1.9.17.

| `title`    | Built. The title of a Ren session, the same locally and on Ren (`Title`).                                                         |
| `controls` | Built. Model picker, `/compact`, archive, delete and fork on a Ren session (`Controls`).                                          |

| build      | Built. `script/build.ts`: the publishable package in `dist`.                                                                      |

## 4. Features, in build order

Each is one commit. Built features leave the list; the others keep their numbers.

- **8. Permissions and questions.** Remote `permission.asked` and `form.created` reach the user (the native prompt if a plugin can raise it, else a dialog through RPC), and the reply goes to `session.permission.reply`, `session.form.reply` or `session.form.cancel`.
- **9. Open and catch up.** `/ren:sessions` lists Ren sessions with search and filters and opens one: import the Ren transcript into a local session with the same ID. On open, a local copy that is behind is removed and imported again. Opening a Ren session calls `Mirror.Service.watch`, and the catch-up also covers what the mirror did not see (L12).
- **11. Attachments.** Local files and pasted images upload with `drive.startUpload` and go in `files` (maximum 10).
- **12. Status and retry.** Starting, failed and stopped states are visible; `/ren:retry` calls `chat.retry`; notifications through the TUI attention API.
- **13. Move a local session to Ren.** A Ren endpoint that creates a session in a space from an OpenCode export (session row and message rows), a new `origin` literal, and the restore of those rows on the brain; then `/ren:move`, and a model change from a local model to `ren/<model>`.
- **15. Panels.** Files, changes, terminal (`/ren:files`, `/ren:diff`, `/ren:shell`), `/ren:background`, links to tasks and pull requests, context usage.

## 5. Limits

- L1. Edit diffs and subagent links show as generic tool rows (F5). A fix needs proxy tools that wait for the remote result, limited to Ren sessions, or an OpenCode change.
- L2. Sender names are a text prefix (F10).
- L3. `@` file search and `!` shell are local (F11). The browser tab is not possible in a terminal.
- L4. Undo and redo: only user message IDs match between local and Ren.
- L5. A queue is local until sent. Other users do not see it.
- L6. Cost is the catalog price (F8).
- L7. Models and server commands are one list for all spaces; the plugin checks the selection at send time. A model that a Ren session's space does not offer fails its turn with Ren's reason when the plugin switches the brain to it. Each location loads its own server part (`ctx.location`), so a server part in another directory is expected to list a newly selected space's models only at its next refresh, within 5 minutes (not run).
- L11. `/ren:space` lists the first 100 joined spaces.
- L8. Presence and fork do not exist in Ren (F14).
- L9. Events lost while the event stream reconnects mid-turn are not replayed into the local message; the turn goes on with the next events, or finishes when the brain is idle. Feature 9 catches a local copy up.
- L12. The mirror shows a message from another client only while the Ren session is watched: from a local turn in this OpenCode process until the brain's idle end of the event stream (F32), at most 4 sessions. A remote turn already running when a session is opened, and messages delivered while it was not watched or while the event stream reconnected, are not shown until feature 9.
- L13. A step of the local session ends at the delivery of another user message, so two messages delivered back to back can leave one local step empty. A synthetic continuation (a subagent's result, a scheduled wake) streams inside the running step, or not at all when no step runs.
- L14. A local prompt during a mirrored turn waits until that step ends (F4), so the local user cannot steer a teammate's running turn from OpenCode.
- L15. Names come from the space's member list, because the Chat API does not expose the `userName` the brain stamps (F31); a channel, schedule, webhook or task message shows its origin.
- L16r. A rename on Ren shows locally only while the session is watched, or at its next connect, which reads the brain's title (L12). A local rename that does not reach the brain within a minute (stopped, failed, unreachable, signed out) stays local and is sent at the session's next connect in this OpenCode process; a restart forgets it, and the brain's title then wins. A Ren rename that arrives while a local rename is on its way is dropped. With the capability `rename` false, a local rename stays local.
- L16c. A switch of a Ren session to a local model is undone, not prevented (OpenCode has no veto, F35c). A prompt never runs on the local model, but a step that an already running execution starts between the switch and the revert can. The plugin tells the user with a notice (a synthetic message), because a server plugin cannot show a toast.
- L17c. A compaction that another client or the brain starts on Ren is not shown in the local session. When a `compaction` agent model is configured to a local model and Ren refuses a compaction, OpenCode summarizes the local history with that model.
- L18c. Ren has no unarchive (F14): unarchiving a local Ren session leaves the Ren session archived, with a notice. Deleting a local copy never changes the Ren session.
- L19c. A fork of a Ren session is local only (F14): it is disconnected from Ren, and its `ren/*` model refuses to run until the user picks a local model.
- L16s. The consent page says "Ren CLI": the plugin signs in as the CLI's client, because the two tools renew one stored login and a refresh token works only for the client that got it (F34s). A client of its own would need a hosted client metadata document, an entry in the server's `ClientMetadataFetch`, and the client recorded with each login in the shared file, which changes the CLI's format.
- L17s. Ren is not an integration in OpenCode's `/connect`: an OAuth method's credential is a second copy of the refresh token in OpenCode's store (F36s), and the two copies cannot both stay valid when either side rotates it (F34s). `/ren:login` shows its own dialog instead.
- L18s. When the server part runs on another machine than the TUI, the browser's redirect to `127.0.0.1` reaches nothing; the user pastes the address from the browser into the sign-in dialog (run with the fake Ren, in tests and by hand in the TUI).
- L19s. After `/ren:logout`, a Ren session's open Chat API connection keeps working until its chat token needs renewing (at most 60 minutes, F13).
- L16b. The supported range is `>=2.2.6 <2.4.0`; 2.3.x is covered by a typecheck of the source against `@opencode/plugin` 2.3.2 only, not run. The published `./rpc` has no type declarations.
