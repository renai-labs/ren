## 2. ren-v1: refresh after a 401

ren-v1 had an after-401 refresh only for subscription seats (Anthropic Max, ChatGPT), not for MCP credentials.

| #   | Fact or failure                                                                                                                                                                                                                   | Evidence                                         | Rule      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | --------- |
| U1  | A 401 names the credential generation that the failed request used. When the stored generation is newer, the 401 belongs to a credential that no longer exists: Ren returns the newer one, calls no provider, and doubts nothing. | `inference/refresh.ts:335-361`, `5c639c61c`      | §9 rule 4 |
| U2  | A 401 observation with a stale generation counts as transient, never as "needs reauth".                                                                                                                                           | `inference/lease.ts:393-394`                     | §9 rule 4 |
| U3  | A refresh result is written only with the lease and the exact generation that was read. A newer generation (a reconnect) wins; the token that the slow writer got is dropped.                                                     | `5c639c61c`                                      | §8 rule 3 |
| U4  | The lease must outlast a token request plus the write of its result; ren-v1 asserted this at module load.                                                                                                                         | `5c639c61c`                                      | §8 rule 9 |
| U5  | Only a confirmed revocation marks a seat for reconnect. A network failure or a 5xx keeps the credential and backs off.                                                                                                            | `5c639c61c`, `d8791547b`                         | §9 rule 6 |
| U6  | An OAuth token with no expiry was never refreshed (`needsRefresh` is false without `expiresAt`).                                                                                                                                  | `vault/CLAUDE.md`, `vault/credential.ts:341-345` | §9 rule 1 |

## 4. OpenCode MCP behaviour

| #   | Fact                                                                                                                                       | Evidence                                 | Rule      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- | --------- |
| O1  | A remote server with `oauth: false` gets no OAuth provider, so OpenCode never starts a sign-in of its own.                                 | `packages/core/src/mcp/index.ts:165`     | §14       |
| O2  | A connect that fails ends in status `failed`, or `needs_auth` for an OAuth error. The server and its tools stay down.                      | `packages/core/src/mcp/index.ts:425-428` | §14       |
| O3  | A config change reconnects only the servers whose config changed (`isDeepStrictEqual`). A failed server with the same config stays failed. | `packages/core/src/mcp/index.ts:518-524` | §14       |
| O4  | The MCP service has `servers()` (with status) and `connect(server)`. A plugin can reconnect one server without a config change.            | `packages/core/src/mcp/index.ts:103-107` | §14       |
| O5  | An MCP session that expires (404) reconnects and runs the call once more. Other errors pass through to the tool call.                      | `packages/core/src/mcp/index.ts:338-353` | §9 rule 8 |

## 8. If ren-v1 credentials ever move to v2

No move is planned (E13, `specs/runtime/e2b-brain/README.md:154`). A move needs its own spec; these are its starting facts.

| Part                       | Moves as is?           | Why                                                                                                                                                                                    |
| -------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Encrypted values           | No: open, then seal    | v1 seals with `VAULT_ENCRYPTION_KEY` and the vault id as authenticated data (`ren-v1/packages/api/src/vault/CLAUDE.md`). v2 seals with `Envelope` and the credential id (README §6.8). |
| Owners                     | Must be mapped         | v1 vault tiers are org, pod and user. v2 owners are org, space and person.                                                                                                             |
| MCP links                  | Must be mapped         | v1 anchors a credential to an `mcpId`. v2 uses `app_id` and `mcp` from PR #51 (K34).                                                                                                   |
| OAuth refresh              | Yes, if tokens survive | Refresh sends no callback address; dynamically registered clients are in the credential (S4).                                                                                          |
| New sign-ins with org apps | No                     | Provider consoles hold v1's callback address (S4).                                                                                                                                     |
| Composio                   | No: connect again      | v1's Composio user id is the Ren user id; v2's is the credential id (K22). A session uses only accounts of its own user (C3).                                                          |
