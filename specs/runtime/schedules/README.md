# Schedules: playbook

This folder is the single source for schedules (REN-1435, milestone "Open-source V1 parity"). An agent that continues this work reads this file first. Update this file in the same change that makes or changes a decision.

## 1. Goal

A person or an agent saves a schedule in a space. At each due time, Ren starts a turn in that space with the saved message, with no person in the chat.

Done when:

- A person creates a daily schedule in the app. At its time, a new chat starts in the space with the schedule's agent and message, and the run shows in the schedule's detail.
- An agent in a chat creates a follow-up "in 30 minutes" for this chat. 30 minutes later the message arrives in the same chat.
- With two Ren servers, each fire starts one chat. A Ren restart loses no fire and doubles none (S30's repeated hour excepted).
- The tests in §10 pass.

## 4. Words

| Word     | Meaning                                                                                             |
| -------- | --------------------------------------------------------------------------------------------------- |
| Schedule | A saved rule: when to run, in which space, with which agent and message.                            |
| Fire     | One due time of a schedule, for example `2026-10-28T09:00:00 Europe/Berlin`.                        |
| Run      | What Ren did for one fire: started a session, skipped it (with the reason), or failed.              |
| Owner    | The person who last wrote the schedule's instruction (S9). The fired turn runs as this person (S8). |
| Target   | Where a fire runs: a new chat, or one existing chat (S6).                                           |
| Ticker   | The loop in each Ren server that finds due schedules and inserts their runs (S1).                   |
| Origin   | The `schedule` field of a message: schedule id, name, scheduled time (S13).                         |

### 5.1 Schema (`@ren/schema/schedule`)

| `Schedule.WhenInput`   | `Schedule.When` or `{ in }`. `in` is `Schema.DurationFromString` (`"30 minutes"`). Core stores it as `{ at: now + in }` (S4).                                                                                                                                       |
| `Schedule.Target`      | `"new-chat"` or `{ sessionId }`. The input also accepts `"this-chat"` (S20).                                                                                                                                                                                        |
| `Schedule.Info`        | `id`, `name`, `spaceId`, `agentId?`, `when`, `target`, `message`, `ownerId`, `status` (`active`, `paused`, `ended`), `pausedReason?` (`user`, `owner_left`, `agent_removed`), `nextRunAt?`, `createdAt`, `archivedAt`, `updatedAt`.                                 |
| `Schedule.Run`         | `id`, `scheduleId`, `scheduledAt`, `startedAt?`, `trigger` (`timed`, `manual`), `status` (`pending`, `started`, `skipped`, `failed`), `reason?` (`previous_run_busy`, `paused`, `archived`, `owner_left`, `agent_removed`, `chat_archived`), `error?`, `sessionId`. |
| `Schedule.Origin`      | `scheduleId`, `name`, `scheduledAt`. `Session.SendInput.schedule` and the Chat API user message carry it, beside `channel` (S13).                                                                                                                                   |

### 5.2 Tables (`@ren/db`)

| Table          | Columns                                                                                                                                                                                                                                                                                                                         | Indexes                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `schedule`     | `id`, `organization_id`, `space_id`, `name`, `owner_id`, `agent_id` (null: space defaults), `cron`, `time_zone`, `until_at`, `run_at` (exactly one of `cron` and `run_at`), `target_session_id` (null: new chat), `message`, `next_run_at` (null: paused or ended), `paused_reason`, `created_at`, `updated_at`, `archived_at`. | `(space_id)` where not archived. `(next_run_at)` where not archived and `paused_reason` is null.                              |

`target_session_id` has no foreign key: S28 finds a deleted chat at the fire. `schedule_run.session_id` has none either: Retention deletes chats on its own clock (S18).

### 5.3 Next fire

One pure function in core, `Schedules.nextFire(row, after)`, gives the next fire instant, or none:

1. A one-time schedule: `run_at` if it is after `after`, else none.
2. A cron: Effect's `Cron` reads the expression in UTC over local wall times; each wall time maps back to the instants that show it in the schedule's time zone: none in the spring-forward gap, two in the repeated fall-back hour (S30). None when the result is after `until`.

The latest missed fire (S2) of a due cron row uses the same mapping backwards from now, and is never before `next_run_at`.

### 5.4 Trigger

`ScheduleTrigger.Service` decides when a schedule fires and records each fire as a pending run. It has `changed(scheduleId)`, which `Schedules` calls after each write, and `claim`, which records the fires that are due. `Schedules` runs the pending runs; a trigger never starts a chat.

`ScheduleTrigger.layerPostgres` (S1): `changed` does nothing. `claim`, in one transaction, selects up to 100 rows with `next_run_at <= now`, not archived, `paused_reason` null, `FOR UPDATE SKIP LOCKED`. For each row it inserts a `timed` run for the latest missed fire (S2) and sets `next_run_at = nextFire(when, now)`.

A later layer (Temporal Schedules, a Durable Object alarm) keeps its own copy in `changed` and inserts the run when its fire arrives; its `claim` does nothing.

Every 30 s, `Schedules` calls `claim`, then `DurableRunner.ensure(ScheduleFire, { runId })` for every `pending` run. `ensure` does nothing for a key that runs or ran (`core/src/durable-runner.ts:7`).

### 5.5 `ScheduleFire`

One durable run per run row, registered with `DurableRunner.register`. Steps, in order; the first that applies ends the run:

1. Read the run and the live schedule (S27). A run that is not `pending` ends here.
2. Archived schedule: `skipped`, `archived`. Paused schedule and a `timed` run: `skipped`, `paused`.
3. The owner does not act in the space (`SpaceQueries.actsIn`, `core/src/space/queries.ts:65`): pause with `owner_left`; `skipped` (S10).
4. The agent is archived or not in the space: pause with `agent_removed`; `skipped` (S11).
5. Existing-chat target, and the chat is archived or gone: archive the schedule; `skipped`, `chat_archived` (S28).
6. New-chat target and a `timed` run: the latest earlier run is `pending`, or its chat is not idle (`SessionRunner.get(...).status`, `core/src/session/runner.ts:169`): `skipped`, `previous_run_busy` (S3, S15).
7. Deliver, as the owner (`sender: { userId, memberId }`, `Actor.memberOf`):
   - New chat: `SessionRunner.create` with the run's session id, the title of S22, `interactive: false`, and `initialMessage` with the run's message id, the message and the origin. `agentId` when set. `AlreadyExists` means an earlier try started it.
   - Existing chat: `SessionRunner.send` with the run's message id, `delivery: "queue"` and the origin. The brain skips a known message id (`cell/src/harness/opencode/harness.ts:324-330`).
8. On `BrainUnavailable` or `BrainRejectedError`: retry with backoff up to 1 minute. Past the deadline (the schedule's `next_run_at`; 1 hour after `scheduled_at` for a one-time schedule or a `manual` run), the run is `failed` with the error (S15). Success: `started`, with `started_at`.

### 5.6 Operations

`Schedules` is a primitive (`core/src/primitive.ts:41-59`): `list` (by space, status, search), `get`, `create`, `update`, `archive`, and the actions `pause`, `resume`, `run`. Runs are their own list primitive, `schedule-run`, because an action answers with the schedule. Every endpoint has `Mcp.Tool` (S20).

| Operation | Effect on the row                                                                                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create`  | Owner = actor. `this-chat` resolves to the root of `actor.agent.sessionId`; a person's `this-chat` is `Invalid`. `{ sessionId }` must be a chat of the same space. `next_run_at = nextFire(when, now)`. |
| `update`  | A change to `message`, `agentId`, `target` or `when` sets owner = actor (S9). A change to `when` recomputes `next_run_at`.                                                                              |
| `pause`   | `paused_reason = user`, `next_run_at = null`.                                                                                                                                                           |
| `resume`  | Clears `paused_reason`; `next_run_at = nextFire(when, now)`, so no catch-up. From `owner_left`: owner = actor (S10). From `agent_removed`: `Invalid` while the agent is still removed (S11).            |
| `run`     | Inserts a `manual` run with `scheduled_at = now`, then ensures its `ScheduleFire` (S16).                                                                                                                |
| `archive` | `archived_at = now`, `next_run_at = null` (S21).                                                                                                                                                        |

A policy document, `core/src/schedule/policy.ts`, allows every action to a space member and nothing to anyone else (access §5). An agent acts as its sender (access §12).

## 6. Decisions

| S1  | The `schedule` row in Postgres is the only copy of a schedule. It holds `next_run_at`. A ticker loop in each Ren server runs every 30 s. ## 7. App

Prior art and parity target: ren-v1 `packages/app/src/features/schedule/` (Scheduled page, schedule card, schedule drawer, `lib/schedule-builder.ts`, `lib/cron-preview.ts`).

### Schedules page (sidebar → Schedules, `/schedules`, clock icon)

1. Subtitle "Work that starts on a schedule instead of a message." Toolbar: search, state filter (any, active, paused, ended), space filter, "Create schedule".
2. A three-column card grid, sorted by name, 9 to a page with numbered pages (ren-v1). A card shows the clock icon, the name, "space · when", and the next run as a relative time; a paused card hides the next run.
3. Card actions: archive, and a switch that pauses and resumes. An ended schedule's switch is off and disabled, with "It ended. Edit its time to run it again."
4. A card opens the detail (S24).
5. Empty state: "No schedules yet. Create one to run a prompt on a recurring cadence."

### Schedule detail (`/schedules/$scheduleId`)

The message, the agent, the owner, `when`, Run now, Edit, pause or resume, archive, and the runs of the last 30 days with status, reason and a link to the chat.

### Schedule drawer

A side drawer, as ren-v1. Order: space (create only), message (focused, "What should the agent do?"), name, agent ("Space defaults"), repeat and time side by side (every hour, every day, every weekday, every week, every month, custom cron, once), days (several, from a menu of checkboxes), day of month (1–31), cron, date (once), the next run ("Next Oct 28, 9:00 AM GMT+1"), time zone (searchable), until date and time (the time is off until a date is set; a date alone ends at 23:59). Submit: "Create schedule" or "Save".

### In a chat

1. The chat menu has "Schedule a message" (S25): the same drawer, with the space and the target fixed to this chat and no agent field.
2. A fired message shows a header, "Scheduled · Daily report · <time>", with a link to the schedule (S13).

Not ported from ren-v1: the model field (S7), the picker for an end time that happens twice on the fall-back day, the words for a custom cron (ren-v1 used `cronstrue`), and "Delete" (v2 archives, S21).

## 8. Lifecycle

| State                                         | What happens                                                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Two Ren servers tick at the same time         | `SKIP LOCKED` gives each row to one server; the unique `(schedule_id, scheduled_at)` stops a second run (S1).                                                      |
| Ren stops inside the tick transaction         | Postgres rolls back. The next tick claims the same fire.                                                                                                           |
| Ren stops after the commit, before `ensure`   | The run stays `pending`. The next tick ensures it (S1).                                                                                                            |
| Ren stops inside `ScheduleFire`               | The durable run resumes on start. A repeated create answers `AlreadyExists`; a repeated send finds the known message id (§5.5).                                    |
| Ren down past fire times                      | The latest missed fire runs once; no rows for the others (S2, S17).                                                                                                |
| Brain asleep                                  | `SessionRunner.create` wakes it through `Brains.start`; a send to a chat not on the brain restarts it from its start input (`core/src/session/runner.ts:128-147`). |
| Brain waking or down                          | `BrainUnavailable`: retry until the deadline, then `failed` (S15).                                                                                                 |
| Previous run mid-turn                         | New chat: `skipped`, `previous_run_busy` (S3). Existing chat: the message waits in the queue (S6).                                                                 |
| Schedule edited, paused or archived mid-retry | The next try reads the live row (S27).                                                                                                                             |
| Owner leaves the space or the org             | The next fire pauses with `owner_left` (S10).                                                                                                                      |
| Agent archived or removed from the space      | The next fire pauses with `agent_removed` (S11).                                                                                                                   |
| Target chat archived or deleted               | The next fire archives the schedule (S28).                                                                                                                         |
| Space archived                                | Its schedules are archived in the same transaction (S29).                                                                                                          |
| Daylight saving change                        | Spring forward: no run at a local time that does not exist. Fall back: a repeated local time runs twice (S30).                                                     |
