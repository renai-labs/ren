# Channels: playbook

This folder is the single source for the work on REN-1441. An agent that continues this work reads this file first. Update this file in the same change that makes or changes a decision.

The end product is one combined spec: the piece specs in this folder, together. A piece spec is written only after the user and the agent finish the discussion of that piece (§2).

## 1. Goal

A person mentions Ren in Slack, Linear or GitHub. Ren runs a turn in a space and answers in the same thread. A reply in that thread continues the same session.

Done when (draft, confirmed piece by piece):

- A Slack mention, a Slack DM, a Linear agent session and a GitHub comment each start a turn and get an answer in the thread.
- A repeated delivery of one event starts one turn.
- A change of the provider (a new place such as email) is a new layer. The core does not change.

Words used here:

| Word     | Meaning                                                                                                                 |
| -------- | ----------------------------------------------------------------------------------------------------------------------- |
| Provider | An external system: Slack, Linear, GitHub.                                                                              |
| Install  | The link between a Ren organization and one provider workspace (Slack team, Linear workspace, GitHub App installation). |
| Place    | Where people talk to Ren in a provider: a Slack channel or DM, a Linear project, a GitHub repository.                   |
| Thread   | One conversation in a place: a Slack thread, a Linear agent session, a GitHub issue or pull request.                    |
| Mapping  | The link from a place to a space (and an agent).                                                                        |
| Sender   | The provider account that wrote the message, and the Ren user that it maps to.                                          |
| Event id | The provider's id for one delivery. A repeated delivery has the same id.                                                |

## 2. How to work

The loop of [`../e2b-brain/README.md` §2](../e2b-brain/README.md#2-how-to-work), one piece at a time, in the order of §3: read, discuss (situation, model, issue, options, recommendation), agree contracts and lifecycle states, write the piece spec (`<letter>-<name>.md`), proceed.

Rules for every piece:

- A ledger row is evidence: a v1 behaviour and its source. Its verdict (keep, changed, drop) is a proposal for another design (B&H). Decide each change against this repo's model (CH2).
- Each provider is a layer of one provider-neutral service. Only `server/src/main.ts` chooses layers.
- Check each claim against the code and give `file:line`.
