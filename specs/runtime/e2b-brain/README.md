# E2B brain: playbook

This folder is the single source for the work on REN-1513. An agent that continues this work reads this file first. Update this file in the same change that makes or changes a decision.

The end product is one combined spec: the piece specs in this folder, together. Agents implement it and run it end to end. A piece spec is written only after the user and the agent finish the discussion of that piece (§2).

## 1. Goal

Chat runs end to end on a brain in an E2B sandbox, and the brain's tools run natively in the same sandbox.

Done when:

- A user creates a session in the app, chats, runs native tools (shell, file edits), reopens the session and continues it.
- The sessions of one space share one sandbox. A space can switch to one sandbox per session.
- A client token reads only its own session and that session's children.
- Sessions sync to Postgres and restore from Postgres when a sandbox is lost.

| Word        | Meaning                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------- |
| Brain       | The harness (OpenCode) and Ren's code around it. It serves one session or all sessions of a space. |
| Harness     | The agent runtime inside the brain. Today only OpenCode.                                           |

| Environment | A machine where tools run. `Native` means the brain's own sandbox.                                 |

## 2. How to work

The loop, one piece at a time, in the order of §3:

1. **Read.** Read this playbook, the v2 code of the piece (§8) and the ren-v1 references of the piece (§8, `ren-v1-hld/references/`). Do not write a spec yet.
2. **Discuss.** With the user, go through the piece: situation, model (ASCII), issue, options, recommendation. Ask each decision with the question tool, after the situation. Record each decision in §6.
3. **Arrive at contracts.** Agree the piece's services (interfaces and errors), their layers and implementation details, and changes to shared contracts (`host-api`, `schema`, `protocol`, `db`). Check every lifecycle state the piece touches: asleep, waking, mid-turn, down, restarting.
4. **Write the piece spec** in this folder (`<letter>-<name>.md`): goal, services and layers, contract changes, lifecycle states, and the list of tests, edge cases included. Mark the piece "Spec written" in §3.
5. **Proceed** to the next piece.

Implementation starts only when the user says so. Then agents implement from the combined spec: tests first, each test fails before its change.

Rules for every piece:

- Every replaceable part is a service with one or more layers (§4): harnesses, brain hosts, sandboxes, environments, models, tokens, storage, scheduling. Code asks for the service. Only a composition root chooses a layer.
- Check each claim against the code and give `file:line`. Look for prior art in `../ren-v1`, `~/Documents/opencode` and `repos/effect` before a new pattern.
- Follow `AGENTS.md`, the package `AGENTS.md` files and the `effect` skill.

## 5. System

```
 app ──① POST /sessions──▶ Ren: Session.create → BrainRegistry (brain of the space) → BrainHost.start
     ──② Session.access──▶ Ren: BrainHost.access → {url, client token}
     ──③ /chat/* (client token)────────────────────────────────▶ sandbox
 Ren ──BrainApi /ren/* (server token)──────────────────────────▶ sandbox
 Ren ◀─RenHostApi /host/* (host token): models.refresh, settings, host.refresh, sync ──── sandbox
 Ren ──SandboxProvider: create · resume · pause · kill─────────▶ E2B
 sandbox: Bun entry → Brain API, Chat API, Scheduler, Sync, OpenCode process profile, native tools
```

Core flows:

| Flow   | Steps                                                                                                                         |
| ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Create | app → `Session.create` → brain of the space (create if none) → `BrainHost.start` → sandbox create or resume → `/ren/sessions` |
| Open   | app → `Session.access` → brain runs? session present? else restore from Postgres → `{url, client token}`                      |
| Turn   | app → `/chat/*` prompt → OpenCode → model → events back over `/chat/*`                                                        |
| Sync   | `Scheduler` → sync step → `/host` sync ingest → Postgres                                                                      |
| Idle   | every session of the brain idle → pause the sandbox; the next call wakes it                                                   |
| Lost   | sandbox gone → new sandbox, next generation → restore sessions from Postgres                                                  |

The harness database in a brain (`HarnessStorage`) is a cache: the brain may delete it at any time, and each chat comes back from Postgres on first access (E98). | As ren-v1: Postgres held the log and the VM rebuilt sessions from it (`ren-v1/packages/api/src/opencode/docs/sessions-and-sync.md`). A local copy that is older than Postgres can then do no harm. |
| E100 | On a harness version change, the brain syncs every chat, then deletes the harness database and starts the new version on an empty one. Workspace files stay. If the sync does not drain, the upgrade waits. Rows in Postgres carry `{ harness, harnessVersion }`; the adapter's `restore` converts rows of an older version. Brain core does the sync, the delete and the restore through the harness adapter's `Transcript` contract (piece J), so a Pi adapter needs no core change. | User decision (piece E). A migration never runs over chat data: OpenCode's `20260604172448_event_sourced_session_input` deletes `session_message` and `event_sequence`, and the next sync would then remove the history from Postgres. ren-v1 shipped OpenCode only in a new VM (`ren-v1-hld/references/13-release-version-skew.md`, rule 4) and converted old rows on read (INV-58). |
| E101 | Sync never hard-deletes in Postgres. A message that is missing from an upload gets `removed_at`; restore and reads skip removed rows. A retention job hard-deletes removed rows 30 days after `removed_at`. Replaces E90's counter guard. | User decision (piece E). Today a commit deletes every message not in the upload (`core/src/session/opencode-store.ts:54`), so a local loss empties Postgres. E90's guard fails once the restarted local counter passes Ren's checkpoint, and its "restore instead" cannot import over an existing chat (`cell/test/opencode-import.test.ts:125`). |
| E102 | Ren deletes a chat, with its children and transcript, 30 days after its last activity (last message or status change). How a brain that still holds the chat in its cache learns of the delete is open (piece E, topic 7). | User decision (piece E). Active chats never expire. |
