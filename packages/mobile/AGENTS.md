# @ren/mobile

The iOS and Android app: Expo SDK 58, React Native and Expo Router.

## Structure

- `src/app/`: Expo Router file routes. A route file default-exports its screen, the one place Ren allows a default export. `sign-in.tsx`, `sign-up.tsx` and `verify-email.tsx` are the only routes outside the `(app)` group; they mirror the web's login, signup and verify-email pages and share `#features/auth/*` and the copy and checks in `AuthForm` (`@ren/client`). The group's layout provides the signed-in user's chat runtime (`ChatReact.runtime`) and a drawer whose content is `#components/sidebar`. Its screens are `index` (a new chat, the home screen), `chats` (search and the full list, the only screen with `#features/chat/new-chat-button`), `chat/[id]`, `settings`, and the `tasks` and `drive` folders, each a Stack with its own `_layout.tsx` (`tasks/index`, `tasks/[id]`; `drive/index` for the root and folders, `drive/file` for the viewer, `drive/artifacts`). Spaces have no screens: they are a picker on the new chat and new task, and a filter or top-level folder in Tasks and Drive.
- `index.ts`: the entry. It installs `globalThis.crypto` from `expo-crypto` (`#lib/crypto`) before Expo Router loads, because Hermes has no `crypto.getRandomValues` and `@ren/schema` makes its ID generator at import.
- `src/components/<name>.tsx`: shared primitives and app chrome (sidebar, header buttons), imported as `#components/<name>`.
- `src/features/<feature>/<name>.tsx`: components that belong to one feature (`chat`, `tasks`, `drive`), imported as `#features/<feature>/<name>`. A component used by two features lives in `components/`.
- `src/lib/<name>.ts`: host code (fetch, storage, lifecycle), imported as `#lib/<name>`.
- `src/global.css`: the Uniwind entry, with the fonts: the system font on iOS (SF Pro, as on the web) and Inter on Android, where SF Pro's licence does not reach, and IBM Plex Mono for code. `app.config.ts` registers the font files through `expo-font`; `Text`, inputs and `Markdown` use `font-sans` and `font-mono`. `src/theme.gen.css` holds `@ren/ui`'s theme, generated by `script/theme.ts`. Run `bun run generate` after a theme change in `@ren/ui`, and never edit the file by hand.
- `src/uniwind-types.d.ts`: written by Uniwind's Metro plugin on every bundle. Commit it when it changes.

## Rules

- Depend on `client`, `chat`, `schema` and `util` only; lint enforces it. When a screen needs logic that sits in `@ren/app` and is not tied to the DOM, move it to the package that owns it (usually `@ren/chat`) and use it from both apps. Never copy it.
- `react-dom` is a dependency only because Expo packages list it as an optional peer: without it in this workspace, Bun's isolated install links two copies of several Expo modules and `expo-doctor` fails. The app never imports it.
- State follows `packages/app/AGENTS.md`: server data in TanStack Query, live chat in `@ren/chat` atoms, everything else in the component that owns it.
- Style with Uniwind classes on the theme's tokens (`bg-background`, `text-muted-foreground`), never a raw colour. Uniwind's platform variants (`ios:`, `android:`) are fine.
- Components come from React Native Reusables' Uniwind registry. Copy the component and adapt it to Ren's rules: `cn` from the `cn` package, `use(Context)` instead of `useContext`, named React imports, and a React Native import that collides with the component's name aliased as `<Name>Primitive`. The Reusables CLI does not fit Ren's layout, so do not use it.
- Sheets come from `#components/sheet`. A list of actions is `#components/menu-sheet` and a list of choices is `#components/option-sheet`; do not build another.
- Auth is Better Auth's Expo client in `#lib/auth`. It keeps the session cookie in `expo-secure-store`. The session is a query (`Auth.sessionOptions`), and `src/app/_layout.tsx` guards the routes on it with `Stack.Protected`. After a sign-in or sign-out, `Auth.refreshSession` refetches it in place, so the routes never see a pending session, and removes every other query; sign-out also calls `ChatReact.forget()`. `src/app/_layout.tsx` keeps the splash screen up until the session resolves.
- Social sign-in (Google, and GitHub and Slack when `sign-in-provider.list` offers them) is `Auth.signInWithProvider`: the Expo plugin opens `/auth/expo-authorization-proxy` in the system browser and the server returns to the app scheme (`callbackURL: "/"` becomes `ren:///`, `ren-dev:///` or `ren-preview:///`). The providers' redirect URIs are the server's, the same as the web's. Brand marks share their paths with the web through `@ren/util/brand-marks`.
- Calls to Ren go through `Api.client` and `Api.query` (`#lib/api`), and those and the chat runtime use `Auth.sessionFetch`. It uses `expo/fetch`, which streams response bodies, and adds the session cookie only for Ren's server.
- Icons match the web's: `@ren/app` maps each Tabler name to a solid 20px Heroicon in `src/icons/heroicons.tsx` and keeps Tabler for the rest. Look the name up there and use the same icon from `react-native-heroicons/mini/<Name>Icon`, or from `@tabler/icons-react-native/<Name>` when the web keeps Tabler (`IconX`). Render either through `#components/icon`. Import each icon from its own entry, never a package root, which loads every icon into the development bundle. `src/tabler-icons.d.ts` types the Tabler entries.
- Device preferences live in `#lib/preferences` (`Preferences.make(key, schema, fallback)` on `expo-sqlite/kv-store`, read with `Preferences.usePreference` (never name a hook `use`: the React Compiler treats `use` as React's conditional `use()` and memoizes the call, which breaks hook order)). Chat preferences share their key, schema and default with the web through `ChatSettings` in `@ren/chat`. The theme preference (light by default, dark or system) is applied with `Uniwind.setTheme` in `src/app/_layout.tsx`; `app.config.ts` sets `userInterfaceStyle` to `automatic`. Every screen must read well in both themes.
- Uniwind's `*-safe` classes read insets that `src/app/_layout.tsx` passes to `Uniwind.updateInsets` from a `SafeAreaListener`. Use those classes instead of reading insets in a component.
- Hermes has no `Intl.RelativeTimeFormat`, `Intl.ListFormat` or `Intl.PluralRules`. Shared code the app reaches must not use them. It also lacks `Array.prototype.toSorted`, which `#lib/hermes` installs from `index.ts`; Expo installs a WHATWG `URL` with `URL.parse` and `URL.canParse`. A production build is the only place a missing API shows up, as `undefined is not a function`.
- Workspace packages import their own files with a `.js` extension. `metro.config.ts` strips it for relative imports outside `node_modules`, so Metro finds the `.ts` file.

## Running

- `bun run start` starts Metro for a development build. Expo Go cannot load this app. `bun run start`, `ios` and `android` set `APP_VARIANT=development`. `bun run ios` and `bun run android` build a development build on the Mac, install it on a simulator, emulator or USB device and start Metro; the iOS simulator needs no EAS build and no Apple account. `bun run check:doctor` checks the Expo dependencies.
- `EXPO_PUBLIC_REN_URL` is the server URL and `EXPO_PUBLIC_REN_APP_URL` the web app's, which the sign-in screen opens to create an account or reset a password (`.env.example`). Both default to production. A phone reaches the machine's LAN address, not `localhost`. The server must trust the app's scheme as an origin (`ren://`, `ren-dev://`, `ren-preview://`), which `server/src/better-auth.ts` does. The chat stream goes to the URL that `chat.access` returns, so a phone needs a server whose brains it can reach.
- EAS builds are limited on the current plan. Start one only when the native side changes (a native dependency, a config plugin, native config in `app.config.ts`, an Expo SDK upgrade), and batch native changes into one build. JavaScript changes reach a development build through Metro, and an installed internal or production build through `bun run update:internal` or `update:production` (see Variants and updates); neither needs a build.
- Android development builds are built on the Mac: with `ANDROID_HOME=~/Library/Android/sdk`, run `bunx expo prebuild --platform android`, then `./gradlew assembleDebug -PreactNativeArchitectures=arm64-v8a` in `android/`. Install the APK with `adb install` over USB, or upload it with `bunx eas-cli upload --platform android --build-path <apk>`, which gives an install link and uses no EAS build. When the phone cannot reach the Mac on the local network, run Metro with `bun run start -- --tunnel` (needs `bunx expo login`). It needs the Android SDK command-line tools (`brew install --cask android-commandlinetools`). iOS development builds come from EAS: `bunx eas-cli build --profile development --platform ios`, after registering the iPhone with `bunx eas-cli device:create`.
- Preview and production builds turn on Expo's tree shaking (`eas.json`), which cuts the bundle from about 10 MB to about 4 MB, most of it `effect`. Check a preview build on a device after adding a library with side effects at import.
- Typed routes live in `.expo/types`, which `bun run start` rewrites. A stale copy after a route change fails the typecheck until Metro runs again, or delete it.
- Check a change with `bun run check` from the repo root. For this package it runs the typecheck, the lint, `check:bundle` (`expo export` for iOS and Android, which catches a broken import or Metro config), `check:generated` (the theme) and `check:doctor` (`expo-doctor`, needs the network). The push hook blocks on the first two and the bundle and theme checks, not on `check:doctor`. Native changes need a new development build.

## Variants and updates

- `app.config.ts` reads `APP_VARIANT`: `development`, `preview` or `production`, and an unknown value throws. Unset means `production`, which is what `expo-doctor`, `expo export` and a bare `expo config` see. Every profile in `eas.json` sets it, and `start`, `ios` and `android` set `development`. Never put it in `.env`: Expo CLI loads that file for every command. `NODE_ENV` cannot pick the variant, because Expo CLI sets it from the command (`development` for `start` and `run`, `production` for `export` and builds).
- A variant is an identity: name, bundle identifier and Android package, URL scheme. `production` is `Ren`, `ai.ren.app` and `ren`, which the push credentials and Firebase are registered for; never change it. `development` and `preview` add `.dev` or `.preview` to the identifier, `-dev` or `-preview` to the scheme and a suffix to the name, so all three install side by side. Everything else is the same, including the slug and the EAS project.
- The scheme is the `expo-origin` that Better Auth's client sends, which `#lib/auth` reads from the app config, and the base of `<scheme>://expo-development-client/?url=` links (the Maestro flows use `ren-dev`). A new variant needs its scheme in `mobileOrigins` in `server/src/better-auth.ts`. Only `development` keeps the dev client's generated `exp+ren` scheme (`addGeneratedScheme`), so the QR code from `bun run start` opens the development app and no other.
- `expo-updates` serves JavaScript and asset changes to installed builds. `runtimeVersion` is the `fingerprint` policy: a hash of everything native (dependency versions, config plugins, native config, the identity), so an update only reaches builds with the same native side. `fingerprint.config.js` keeps Expo's `balanced` preset and also ignores `package.json` scripts and `.gitignore`, which the preset hashes: without it, editing any script would change the runtime version. When the native side changes (see the EAS builds bullet), make new builds; builds with the old hash stop receiving updates, and `eas update` publishes to the new hash. Check the hash with `APP_VARIANT=production bunx expo-updates fingerprint:generate --platform android`.
- Each EAS profile has its own channel: `development`, `preview`, `internal` and `production`. `internal` and `production` build the same app, so they share a runtime version, but they go to different people: publish to `internal` with `bun run update:internal -- --message "<message>"`, check it, then promote the same bundle with `bunx eas-cli update:republish --channel internal --destination-channel production`. Both scripts bundle as the profiles build (production variant, production URLs, tree shaking), because `eas update` ignores `eas.json`. Keep them in step with the `internal` profile.
- `expo-updates` checks on launch, and `#lib/app-updates` also checks when the app returns to the foreground, at most every 15 minutes, and downloads in the background. A downloaded update applies on the next cold start, or when the app returns after 5 minutes or more in the background, so it never reloads while someone is using it. Settings shows the running update and a Check for updates row. A development build still loads from Metro. Updates reach it only through the Extensions tab of the dev client.
- Only an EAS build (`eas build`, or `bun run build:android:internal`, which runs it with `--local`) writes the channel into the app. A plain `expo prebuild` and `./gradlew assembleRelease` makes an app that asks for no channel and receives no updates, so never share one.

## Testing

- This package has no unit or component tests. Pure logic is tested in the package that owns it.
- Maestro flows in `maestro/` cover starting a chat, reading the streamed reply and continuing it, with the session already on the device. Run them against a signed-in development build on a device or emulator that `adb` sees, with Metro running and `adb reverse tcp:8081 tcp:8081`: `maestro test maestro/chat.yaml -e METRO_URL=http%3A%2F%2Flocalhost%3A8081`. Each run starts a new chat on the server the app uses.
